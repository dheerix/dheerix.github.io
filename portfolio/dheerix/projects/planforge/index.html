Engineering product case study · Independent product

PlanForge

Turning distributed engineering intent into versioned plans, repository-scoped work, and evidence-backed delivery findings.

Ownership
Creator and product engineer
Status
Working early-stage product
Domains
Developer tools · workflow systems · evidence · agentic engineering

Problem

Features spanning repositories lose shared intent as requirements become tickets, pull requests, implementation details, and separate review conversations.

My ownership

I conceived, designed, and built PlanForge as a versioned planning and evidence control plane, including its schemas, validators, deviation lifecycle, review surfaces, and test suite.

Current outcome

The working implementation persists cross-repository plans, collects delivery evidence, detects reviewable deviations, and renders read-only project and finding views.

01 · Product problem

Local delivery can look complete while system-level intent has drifted.

Intent is fragmented

Requirements, architecture choices, ownership, tickets, code changes, and verification evidence live in different systems and decay at different rates.

Repository views are partial

A pull request can be correct in isolation while violating a contract, dependency, lifecycle requirement, or acceptance criterion shared with another repository.

Completion is ambiguous

One merged change does not prove every required change is merged, and merged code does not prove end-to-end behavior was verified.

Automation can overclaim

Diffs provide useful evidence but cannot always prove business meaning. A trustworthy product must preserve uncertainty and keep engineers in control.

02 · System at a glance

A durable comparison loop around existing workflow systems.

PlanForge does not replace product planning, code review, or engineering judgment. It preserves a versioned baseline and compares implementation evidence against it.

03 · Key decisions

Product boundaries matter more than adding agents.

Deterministic state and workflow authority remain separate from probabilistic interpretation, making findings explainable and recovery deliberate.

Control plane, not project tracker

Coordinate evidence without replacing authoritative systems.

Approach: derive planning and delivery overlays while existing systems retain product workflow and code-review authority.

Trade-off: less direct automation in exchange for clear ownership boundaries.

Central plan + projections

Keep shared intent central and repository work local.

Approach: freeze one versioned plan and generate deterministic repository-scoped projections.

Trade-off: stronger consistency requires regeneration and freshness validation.

Findings, not verdicts

Preserve uncertainty in plan-versus-code comparison.

Approach: classify results as confirmed, suspected, or questions with confidence, provenance, and review state.

Trade-off: human review remains necessary, but evidence is safer and more trustworthy.

Completion ≠ verification

Aggregate every required change and track proof separately.

Approach: derive implementation completion from the full required change set and model verification independently.

Trade-off: accuracy requires explicit optional and superseded evidence relationships.

05 · Product outcome

A working evidence loop, with its limits visible.

Implemented

Versioned plans, repository projections, evidence inputs, deviation rules and lifecycle, durable analysis, workspace discovery, read-only servers, HTML views, and CI-backed tests.

Demonstrated

Generalized examples exposed a cross-repository contract mismatch and a missing durable-state recovery path that local ticket completion could overlook.

Verified

The recorded full test suite passed across foundation behavior, execution-plan validation, workspace discovery, server behavior, and deliberately invalid artifact states.

Not yet proven

Autonomous execution, automatic remediation, production-scale freshness, live multi-user operation, and one canonical project from plan through independent verification.

07 · Learning

What building the product clarified.

Durability before autonomy

Agents become useful only after identity, state, dependencies, approvals, evidence, and recovery are explicit. Conversation history is not a workflow store.

Uncertainty is product data

A suspected mismatch, its confidence, and its provenance are more useful than an unsupported automated verdict.

What I would test next

Run one canonical feature through frozen intent, every projection, all linked changes, one reviewed deviation, and final independent verification.

Re-evaluation trigger

Change the control-plane boundary only when automation has sufficient evidence quality, recovery semantics, and a clear product reason to own workflow transitions.
