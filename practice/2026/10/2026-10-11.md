## Transactions, concurrency, and isolation

### Transaction vs isolation
Scenario: two transactions both read inventory = 1 and attempt to reserve the final item.

**Bharat:** "in both transactions - read count is - even with transaction they both can discount the inventory. this is atomicity not locking per the business requirement"

**Grade: 🟢** Core reasoning correct. Refinement: atomicity means each transaction is all-or-nothing; it does not by itself prevent two concurrent transactions from observing the same state. The missing guarantee is sufficient isolation/concurrency control.

### Optimistic vs pessimistic concurrency
**Bharat:** "either could work - A is pessimist locking, B is optimistic locking. the choice depends on how frequent the conflict can happen - if its rare - B"

**Grade: ⭐** Correct mechanism and trade-off. Prefer the term optimistic concurrency: conflicts are allowed and detected rather than necessarily locking.

### Read Committed / non-repeatable read
A reads price $20k; B updates to $21k and commits; A reads again.

**Bharat:** "A can read either value depdneing on when transaction B finally finishes. If before -it should get 21000. problem would be the processing happened on previous value"

**Grade: 🟢** Correct. Canonical term: non-repeatable read.

### Phantom read
A counts AVAILABLE vehicles = 100; B inserts another matching row and commits; A repeats query and gets 101.

**Bharat:** "it shouldn't matter here - reading a count is different than reading a specific vehicle and updating the same vehicle. Issue could arise if the processing done depends on total vehicles"

**Grade: 🟢** Good business-invariant reasoning. Difference: the matching row set changed rather than an existing row's value. Canonical term: phantom read.

Isolation vocabulary introduced:
- Dirty read: uncommitted data observed.
- Non-repeatable read: same row read twice with different committed values.
- Phantom read: same predicate returns a changed matching row set.
- Read Uncommitted → Read Committed → Repeatable Read → Serializable as increasing isolation mental model.

## EF Core / query behavior

### N+1
Given 500 Vehicles followed by access to `vehicle.Dealer.Name`, initial answer suspected missing index on Status.

**Grade: 🟡 initially.** Index was a valid production consideration, but missed the key symptom: many small queries.

After lazy-loading clue:

**Bharat:** "oh, each line is accessing Dealer table to fetch the name from foreign key"

**Grade: 🟢** Correct. Canonical term: N+1 query problem. Distinguish one/few slow queries (query plan/index/data volume) from hundreds of small queries (chatty/N+1 access).

### Deferred execution
**Bharat:** "until the await tolist - we are just building the query"

**Grade: 🟢** Correct. LINQ/EF query is composed until a materialization/execution point such as `ToListAsync()`.

### IQueryable / premature materialization
Comparison: filter before `ToListAsync()` vs materialize millions of rows and then filter in memory.

**Bharat:** "so should not be calling first query"

**Grade: 🟡** Correct direction; needed explicit articulation that materialization is the execution boundary and subsequent LINQ over the list executes in application memory.

Repository scenario: active vehicles materialized before caller applies dealer/sort/limit.

**Bharat:** "the query can be deffered more by adding an extra Where(dealer => dealrerName).SortBy().Limit(20)"

**Grade: 🟢** Correct. Preserve database-side composition until necessary. Architectural nuance: returning `IQueryable` can leak persistence concerns; use-case-specific query APIs or Specification can preserve boundaries.

### Change tracking
Asked how EF knows which loaded entities changed and why read-only queries may not need that machinery.

**Bharat:** "unsure"

**Grade: ❌ — revision bank.**

Learned: DbContext Change Tracker tracks entity state/original state and supports detecting modifications for `SaveChangesAsync()`. Tracking costs CPU/memory. `AsNoTracking()` is useful for read-only entity queries. DTO scalar projections generally do not materialize tracked Vehicle entities, so don't blindly add it everywhere.

## Database performance / indexes

Query:
```sql
SELECT Id, Price
FROM Vehicles
WHERE DealerId = 42
  AND Status = 'ACTIVE'
ORDER BY CreatedAt DESC
LIMIT 20;
```

### Evidence before optimization
**Bharat:** "Status is string comparison that slows it the most - we can instead get all vehicles and then filter by status in dto"

**Grade: ❌.** Pulling 50M rows into application memory would worsen network, memory, CPU, and latency. A string predicate is not automatically the dominant cost.

Correction: inspect the execution/query plan (`EXPLAIN`, `EXPLAIN ANALYZE`, platform tooling) to determine scans/seeks, rows examined, filters, sorts, and estimates before changing indexes.

### Composite index
Given full scan and query shape `DealerId = ? AND Status = ? ORDER BY CreatedAt DESC LIMIT 20`:

**Bharat:** "dealerId + status ?"

**Grade: 🟡.** Good start. Strong candidate: `(DealerId, Status, CreatedAt DESC)` so filtering and ordering can potentially be served by the index and stop after 20.

For a new query without Status:

**Bharat:** "then we can either compose index of dealerId+createdAt only or keep the status as third"

**Grade: 🟢.** Correct ordering principle. `(DealerId, CreatedAt DESC)` naturally serves the new access pattern; index design should consider the overall workload and write/storage cost, not create an index for every predicate.
