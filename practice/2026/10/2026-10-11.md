## Transactions, concurrency, and isolation

### Transaction vs isolation
Scenario: two transactions both read inventory = 1 and attempt to reserve the final item.

**Bharat:** "in both transactions - read count is - even with transaction they both can discount the inventory. this is atomicity not locking per the business requirement"

**Grade: 🟢** Core reasoning correct. Refinement: atomicity means each transaction is all-or-nothing; it does not by itself prevent two concurrent transactions from observing the same state. The missing guarantee is sufficient isolation/concurrency control.

### Optimistic vs pessimistic concurrency
**Bharat:** "either could work - A is pessimist locking, B is optimistic locking. the choice depends on how frequent the conflict can happen - if its rare - B"

**Grade: ⭐** Correct mechanism and trade-off. Prefer the term optimistic concurrency: conflicts are allowed and detected rather than necessarily locking.

### Read Committed / non-repeatable read
A reads price $20k; B updates to $21k and commits; A reads again.

**Bharat:** "A can read either value depdneing on when transaction B finally finishes. If before -it should get 21000. problem would be the processing happened on previous value"

**Grade: 🟢** Correct. Canonical term: non-repeatable read.

### Phantom read
A counts AVAILABLE vehicles = 100; B inserts another matching row and commits; A repeats query and gets 101.

**Bharat:** "it shouldn't matter here - reading a count is different than reading a specific vehicle and updating the same vehicle. Issue could arise if the processing done depends on total vehicles"

**Grade: 🟢** Good business-invariant reasoning. Difference: the matching row set changed rather than an existing row's value. Canonical term: phantom read.

Isolation vocabulary introduced:
- Dirty read: uncommitted data observed.
- Non-repeatable read: same row read twice with different committed values.
- Phantom read: same predicate returns a changed matching row set.
- Read Uncommitted → Read Committed → Repeatable Read → Serializable as increasing isolation mental model.

### Connection pooling

Initial reasoning correctly identified I/O waiting, then refined to the actual bottleneck: requests can queue waiting to acquire a pooled DB connection even when DB CPU and query execution are healthy.

**Grade: 🟢.**

### Pagination
For a deep query such as `OFFSET 199980 FETCH 20`:

**Bharat:** ordering is required even for the first page, but fetching farther rows requires more traversal.

**Grade: 🟡 → concept corrected.**

Deep offset pagination may require traversing/scanning and discarding a large number of qualifying rows before returning the requested page.

Keyset/cursor alternative: use the last `(CreatedAt, Id)` as the continuation boundary and query the next ordered slice. `Id` provides a deterministic tie-breaker when `CreatedAt` is not unique.

Trade-off: offset supports arbitrary page jumps; cursor/keyset pagination is excellent for next/previous traversal but does not naturally support arbitrary deep page jumps.

# Messaging + Distributed Systems I

## At-least-once delivery and idempotency
Scenario: consumer performs a side effect, crashes before ACK, then receives the same event again.

Learned:
- No ACK can cause broker redelivery.
- At-least-once delivery therefore permits duplicates.
- Idempotent processing makes repeated delivery of the same logical event produce the intended business effect only once.

For same-database work such as decrementing inventory plus recording `EventId`, both operations belong in one transaction.

**Bharat:** identified a transaction as the mechanism that makes the business update and processed-message record succeed/fail together.

**Grade: 🟢.**

Canonical pattern: Inbox / Processed Messages / Idempotent Consumer.

## Cross-system side effects
A local SQL transaction cannot atomically include an external payment API.

Use a stable idempotency key such as `payment-for-order-123` so retries do not double-charge.

## Saga
Saga = sequence of local transactions across service boundaries. Already committed steps are reversed, when necessary, through compensating business actions rather than SQL rollback.

Examples:
- reserve seat ↔ release seat
- charge payment ↔ refund
- create shipment ↔ cancel shipment

Orchestration centralizes workflow state and compensation logic; choreography distributes reactions across services.

Important reasoning:
- A failed step does not automatically mean compensation.
- Transient failure → retry/backoff.
- Permanent business failure → compensate.
- Exhausted retries → DLQ/manual intervention/reconciliation as appropriate.

Shipping creation succeeded but response was lost:

**Bharat:** "retry duplicate and idempotency to be applied"

**Grade: ⭐.**

When shipping creation temporarily failed:

**Bharat:** retrying the shipping job is preferable because this can be eventual consistency.

**Grade: ⭐.**

## Eventual consistency
Temporary disagreement between services can be acceptable when a reliable mechanism drives convergence through retries, durable events, reconciliation, or compensation.

Senior framing: eventual consistency is deliberate convergence, not hope. Business invariants determine where temporary inconsistency is acceptable.

## Transactional Outbox
Failure window: Order commits successfully, process crashes before publishing `OrderCreated`.

**Bharat:** record the intent to publish "in same transaction where we insert order."

**Grade: ⭐.**

Transactional Outbox:
- write business state + outbox row in one DB transaction,
- background publisher sends pending events,
- mark publication progress afterward.

Outbox closes the DB-commit/event-publish gap but does not eliminate duplicates. If publication succeeds and the publisher crashes before recording completion, the event may be published again.

Producer Outbox + at-least-once broker + consumer Inbox/idempotency is the larger reliability model.

## Consumer groups
Classic partition-ownership mental model:
- Within one consumer group, one partition has at most one active consumer at a time.
- One consumer may own multiple partitions.
- If consumers > partitions, extra consumers cannot increase partition-processing parallelism.

4 partitions + 10 consumers:

**Bharat:** initially suggested multiple consumers could share each partition.

**Grade: ❌ → corrected.**

Separate applications such as SearchIndexer and AnalyticsService that both need every event should use separate consumer groups because they are separate logical subscriptions/business purposes, not because they run in separate pods.

Visualization locked:
- `PriceChanged(V123)` is stored once in its partition.
- Search group independently consumes that partition.
- Analytics group independently consumes that same partition.
- Each group maintains independent progress.
- "1 partition → 1 consumer" means at most one active consumer **within a particular consumer group** in the classic model.

## ACK / offset timing
Scenario: receive offset 100 → ACK/commit 100 → start processing → crash.

**Bharat:** "It will retry only price change event, and consumer application don't have the vehicle"

**Grade: ⭐.**

Correct: acknowledging before successful processing can cause the business effect of event 100 to be lost. A later PriceChanged may arrive while the projection never successfully created the vehicle.

Reverse order: process successfully → crash before ACK.

**Bharat:** "Redelivery, but then idempotency must be implemented"

**Grade: ⭐.**

Trade-off:
- ACK before processing → loss window / at-most-once-style risk.
- Process before ACK → redelivery/duplicates / at-least-once → idempotency required.

ACK boundary principle:
**Acknowledge only when the system can safely say broker redelivery is no longer required.**

## Consumer lag and backpressure
Producer 10k events/sec, consumers process 6k/sec → backlog grows by ~4k/sec.

Investigation proposed by Bharat:
- inspect transactional/business work per event,
- determine whether DB is slowing processing,
- inspect consumer instance capacity and vertical scaling.

**Grade: 🟢 production reasoning.**

Additional checks:
- partition count and distribution,
- hot keys/skew,
- downstream API/DB capacity,
- recent traffic or code changes,
- payload/processing-cost changes.

Do not acknowledge early merely to improve lag metrics.

Backpressure principle: bound consumer concurrency/rate so a fast broker does not overwhelm a slower downstream. `SemaphoreSlim` is one simple .NET mechanism for bounding concurrency.

Given:
- consumer CPU 25%,
- memory normal,
- DB/external APIs healthy,
- P0 lag 1,200,000 while P1/P2/P3 ~250–400,

**Bharat:** "No, it's the partition skew problem"

**Grade: ⭐.**

Adding consumer pods may not help because P0 still has one active owner in the ordering model. Investigate partition-key distribution and whether the ordering boundary genuinely requires the hot key to remain together.
