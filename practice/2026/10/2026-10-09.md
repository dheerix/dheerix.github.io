## Q17 — lock + await

Initial answer: lock was described as locking a block to a thread while await releases the thread.

**Grade: 🟡**

Correction:
- `lock` provides mutual exclusion for code coordinating on the same lock object.
- Normal `lock` / Monitor is thread-affine: the acquiring thread must release it.
- An await may suspend on T1 and resume on T47, so a monitor cannot safely span an await boundary.
- For async mutual exclusion, `SemaphoreSlim.WaitAsync()` is permit-based and can be held logically across an await.

Recall gap: when asked for the async primitive, initially answered `Task.Run`.

**Grade: ❌ → repaired to 🟢 after explanation.**

Revision target: distinguish `Task.Run` (queue work to ThreadPool) from `SemaphoreSlim` (permits / bounded async concurrency).

## Async exception propagation

Initial answer incorrectly said exception was not represented by the Task.

**Grade: 🟡**

Correction:
- unhandled exception escaping `async Task` faults the returned Task;
- awaiting a faulted Task observes it and rethrows the exception;
- caller can catch it normally.

Follow-up initially confused `Observed` with Task state.

Revision target:
```text
async method throws
→ Task becomes Faulted
→ await rethrows
→ caller catches
```

## Revision bank / unexpected retest

1. **`lock` terminology:** mutual exclusion around a critical section for code using the same lock object; not “locking a variable/block to a thread.”
2. **`SemaphoreSlim`:** permit-based async coordination / bounded concurrency; `WaitAsync` does not require blocked waiting threads.
3. **Faulted Task:** async Task exception → Task Faulted → await rethrows.
4. **`Task.Run`:** queues work to ThreadPool; useful for CPU-bound UI responsiveness, not an ASP.NET scalability mechanism.
5. **Async I/O:** async does not increase downstream DB/API capacity.
6. **Business independence before concurrency:** code-level independence is insufficient; check invariants, ordering and partial failure.
