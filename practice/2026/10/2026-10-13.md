# Practice — 2026-10-13

## Curriculum position
System Design deep dive — scenario #2: large asynchronous vehicle CSV import.

## Carry-over
Continued the requirements → technical problems → mechanisms → failure/recovery flow from the live viewer-count design.

## Scenario
A dealer uploads a CSV containing up to ~500,000 vehicles / potentially ~1 GB. Processing may take minutes. Every row is validated/imported, progress must survive browser reloads, and the dealer can download a success/failure report.

## Requirement Hat — actual reasoning

### User answer
Asked:
- Is a long-running asynchronous/background process acceptable, with progress shown?
- Are CSV columns/variants fixed?
- What are the validation rules?
- Does the report need overall success/failure counts or row-level detailed errors?

### Grade
⭐ Strong requirement discovery.

### Correction / extension
Do not choose background processing before confirming that completion inside the request is not required. Also clarify:
- partial success vs all-or-nothing,
- duplicate/re-upload semantics,
- exact progress semantics,
- concurrency / number of simultaneous uploads.

Assumptions used:
- async processing is acceptable,
- schema is fixed/versioned,
- partial success is allowed,
- failed rows need detailed errors,
- re-upload must not duplicate vehicles,
- progress means rows processed,
- user may leave and return,
- report retained 30 days,
- hundreds of concurrent uploads are possible.

## Technical decomposition — actual reasoning

### User answer
Identified:
1. durable job status per user because progress must survive new tab/reload; realtime update while browser is open; stages such as parsed → columns validated → imported,
2. schema versioning/backward compatibility,
3. duplicate semantics including overwrite/error and duplicate IDs inside one file,
4. queued state/fairness because hundreds of simultaneous uploads can leave a job at 0% before processing begins.

### Grade
⭐

### Canonical terminology
- durable job state / job lifecycle,
- progress state propagation,
- schema versioning / backward compatibility,
- idempotency and duplicate/conflict semantics,
- work scheduling / queueing / fairness,
- queued vs processing are different states from progress percentage.

Example lifecycle:

```
UPLOADED → QUEUED → VALIDATING → PROCESSING → COMPLETED
```

## Large upload boundary

### User answer
Questioned sending a 1 GB file through the API and noted practical upload limits/firewall constraints.

### Grade
🟡 Correct architectural direction; browser size itself is not the main universal constraint.

### Correction
The stronger reason is to avoid proxying a huge byte stream through API instances, gateways and request timeouts.

```
Browser → API: create import job
API → Browser: JobId + authorized upload destination
Browser → Object Storage: file bytes directly
Upload complete → asynchronous processing
```

Canonical principle:

> Control plane through the API; data plane directly to object storage.

AWS mapping: S3 presigned upload; multipart upload for large objects.

## Worker crash and checkpointing

### User answer
Persist the last processed row/ID so another job/worker can resume.

### Grade
🟢

### Canonical terminology
Checkpoint / processing cursor.

Important correction: checkpointing answers **where to resume**; idempotency answers **whether repeated work around the checkpoint boundary is safe**.

A crash after persisting a vehicle but before advancing the checkpoint can replay the row.

Possible identities:
- `(JobId, RowNumber)` — processing identity,
- `(DealerId, ExternalVehicleId/VIN)` — business identity.

Checkpoint frequency is a trade-off: more frequent checkpoints reduce replay but increase persistence overhead.

## Multi-tenant fairness

### User answer
Connected one dealer submitting many jobs to hot-key/skew thinking and proposed a per-DealerId concurrency limit using SemaphoreSlim-like control.

### Grade
⭐ Good transfer from previous concepts.

### Correction
A local `SemaphoreSlim(3)` limits concurrency only inside one process. Three worker pods could each admit three operations.

Canonical terminology:
- multi-tenant fairness,
- noisy-neighbor problem,
- per-tenant concurrency limit / bulkhead,
- shared scheduling or distributed coordination for a global limit.

> Correct algorithm locally does not imply correct coordination globally.

## Parallel chunk processing

### User answer
Immediately recognized that once chunks execute out of order, one file-level `LastProcessedRow` is no longer a valid checkpoint. Track chunk status instead.

### Grade
⭐

Conceptual model:

```
ImportJob: JobId, Status, TotalChunks, CompletedChunks...
ImportChunk: JobId, ChunkId, StartRow, EndRow, Status, RetryCount, SucceededRows, FailedRows
```

Canonical principle:

> Checkpoint granularity should align with the independently retryable work unit.

Before parallelizing, also verify business independence: duplicate VINs across chunks, row dependencies, ordering requirements, shared DB/downstream capacity.

## At-least-once delivery and idempotency

Scenario: chunk C2 commits all changes and is marked COMPLETED, then worker crashes before ACK. Queue redelivers C2.

### User answer
Before processing, check idempotency/status: if `J100:C2` is already COMPLETED, skip it. If a chunk is replayed after partial work, each persisted row also needs an idempotent key/check before insert.

### Grade
⭐

Canonical mapping:
- chunk boundary → idempotent consumer,
- row boundary → stable processing/business identity,
- ACK after durable completion can cause redelivery but not duplicate effect when processing is idempotent.

Important distinction:
- idempotency key = has this operation already been applied?
- business uniqueness constraint = may this business entity exist more than once?
They can overlap, but are not inherently the same thing.

## Failure classification

Scenario:
1. Price <= 0
2. Vehicle DB timeout
3. structurally corrupted CSV

### User answer
1. Log row error and continue — data error, no retry.
2. Retry exponentially for N attempts — transient error.
3. Log and fail; challenged the wording because a file-level structural/parser error should ideally have been caught earlier rather than appearing arbitrarily as one row.

### Grade
⭐ Including the challenge to the scenario.

### Canonical model
- deterministic business/data validation error → row failure, continue when partial success is allowed,
- transient infrastructure failure → bounded retry + exponential backoff + jitter,
- file-wide schema/structural failure → reject during early file validation,
- recoverable malformed individual row → row failure only if parser can safely recover the next record boundary.

> Validate a failure at the earliest boundary where it can be determined.

## Dependency outage vs queue retry

User correctly selected circuit breaker for a sustained DB outage, then asked how long the queue itself would keep redelivering.

Important distinction:

```
dependency retry count != message delivery count
```

A worker can retry a DB call three times, fail the message, and the broker can later redeliver the whole message according to its independent redelivery/retention/dead-letter policy.

During a broad DB outage:
- circuit breaker protects DB by failing fast,
- slow/pause consumption or delayed redelivery prevents queue/worker churn,
- do not rapidly DLQ thousands of otherwise-valid chunks just because a shared dependency is temporarily unavailable.

Canonical distinction:
- infrastructure outage → backpressure/delay/pause and recovery,
- poison/unrecoverable work item → bounded deliveries → DLQ.

## Progress propagation

### User answer
SSE is still appropriate because after upload the processing is server-side and progress flows server → browser.

### Grade
🟢

Durable job/chunk state remains source of truth; SSE is the responsive notification path.

```
Job DB/current state → SSE → Browser
Browser reconnects → GET current job state → converge
```

No need to replay every intermediate percentage.

> Durable state for correctness; push channel for responsiveness.

When challenged about updating progress per row, user correctly caught that the design had already chosen chunk-level progress rather than 500,000 writes to one job row.

### Grade
⭐

## Why a durable queue instead of Task.Run?

### User answer
`Task.Run` can crash/timeout and lose active chunk processing; retry would need another POST or a separate worker/scanner checking incomplete jobs. With a queue, another pod can start/resume the chunk.

### Grade
⭐ Core architectural reason identified.

Canonical answer:
A 40-minute business-critical import should not be owned by an in-process task whose lifetime is coupled to an API pod. A durable work queue provides:
- durable work ownership,
- redelivery after worker failure,
- decoupling from request/API lifetime,
- independent worker scaling,
- load leveling,
- backpressure.

## .NET / AWS connections

| Architecture concept | .NET / AWS grounding |
|---|---|
| Request lifetime should not own 40-minute work | Avoid fire-and-forget `Task.Run` from ASP.NET request |
| In-process background worker | `BackgroundService` / `IHostedService` — useful, but still process-lifetime scoped unless work source is durable |
| Bounded local concurrency | `SemaphoreSlim` — per-process only |
| Durable work dispatch | SQS / RabbitMQ / Pulsar-style queue + .NET worker |
| Large-file handoff | S3 presigned URL + multipart upload |
| Cancellation | `CancellationToken` for worker shutdown/operation cancellation; not a substitute for durable recovery |
| Transient dependency failure | `HttpClient` resilience / Polly-style retry, backoff, jitter, circuit breaker |
| Atomic local state | EF Core transaction for related vehicle/result/checkpoint writes where they share one DB boundary |
| Idempotency | unique constraints / processed-operation records / conditional write semantics |
| Worker service | .NET Worker Service + `BackgroundService.ExecuteAsync` consuming durable messages |
| Progress push | ASP.NET Core SSE endpoint; durable Job DB remains truth |
| Scale-out | multiple worker pods/instances competing for durable queued work |
| Graceful shutdown | host cancellation token; unacked work becomes recoverable/redeliverable rather than disappearing |

# System Design #3 — Read Scaling, Caching and Invalidation

## Scenario
VDP reads are much higher than writes. At auction peaks PostgreSQL CPU/query latency rises.

## Actual reasoning and grades

- User separated auction status/current bid price from descriptive vehicle data because their staleness tolerances differ. **⭐**
- Before accepting Redis, user asked whether the existing DB query is actually expensive, including whether it performs joins. **⭐**
- On write, user proposed updating cache with latest values. **🟢** Valid, but projection reconstruction/coupling led to cache-aside invalidation.
- For DB commit + failed cache invalidation, user recalled Saga. **🟡** Corrected to Transactional Outbox: reliably propagate a committed state change. Saga coordinates a distributed business workflow/compensation.
- For concurrent stale cache repopulation, user proposed a lock. **🟡** Valid mechanism, but C# lock is process-local; distributed coordination may be unnecessary if bounded staleness is acceptable.
- For a hot-key cache stampede, user proposed SemaphoreSlim. **🟡** Good local mechanism; canonical pattern is request coalescing/single-flight. Per-pod coordination may be sufficient.
- User correctly explained TTL jitter as spreading expirations/repopulation load over time. **🟢**
- During Redis outage, user identified that DB fallback can overwork DB and block/queue requests. **🟢** Canonical: cascading failure, resource saturation, connection-pool exhaustion, bounded fallback.
- User correctly rejected pre-populating all 10M vehicles. **🟢** Cache-aside/lazy population keeps the working set.

## Durable terminology

### Observe before cache
Investigate query plan, indexes, joins, EF-generated SQL/projections, DB CPU/I/O, query latency, connection-pool pressure and access skew before adding cache.

> Observe bottleneck → optimize data access → cache repeated expensive reads when justified.

### Read model / projection
Different fields in one API response can have different consistency requirements. Static-ish VDP details may be cached while auction status/price use a near-current authoritative path.

### Cache-aside
Read: cache → miss → DB/read model → populate cache.
Write: commit authoritative DB → invalidate cache.

### Transactional Outbox vs Saga
- Outbox: reliably propagate a committed state change/event.
- Saga: coordinate distributed business steps, often with compensation.

### Bounded staleness
For non-critical descriptive data, finite TTL + invalidation + eventual convergence may be preferable to distributed locking.

### Cache stampede / thundering herd
Many requests miss the same hot key and simultaneously hit origin.

### Request coalescing / single-flight
Allow one request per key/coordination scope to rebuild while peers wait/reuse result. .NET local mechanism: per-key SemaphoreSlim.

### TTL jitter
Randomize expiry around the base TTL to prevent synchronized mass expiration.

### Cache outage / cascading failure
Naive cache→DB fallback can overload DB. Protect with circuit breaker, bounded fallback/bulkhead, capacity limits and graceful degradation.

### Working set
Cache the actively accessed subset rather than pre-populating the full dataset.

## .NET connections
- EF Core projection/Include/query plan/index reasoning before caching.
- IDistributedCache/Redis-style cache-aside.
- SaveChangesAsync before cache invalidation when DB is authoritative.
- EF transaction + Outbox row for reliable post-commit propagation.
- lock / SemaphoreSlim are local process coordination.
- per-key SemaphoreSlim can implement local single-flight.
- HttpClient resilience concepts generalize to cache/dependency circuit breaking.
- DB connection pool is a scarce bounded resource; uncontrolled fallback can exhaust it.

## Exit status
Read scaling + caching + invalidation: **DONE**.
