## Routing, binding, and validation

Worked through endpoint selection and the difference between route constraints and parameter types.

Key correction:
- `{id:int}` participates in **route matching**.
- `int id` participates in **model binding/conversion**.
- Literal route segments such as `search` are more specific than unconstrained parameter segments such as `{id}`.
- With `[ApiController]`, a route that matches but cannot bind `"banana"` to `int id` normally produces 400.
- With `{id:int}`, the route itself does not match `banana`; if no other endpoint matches, the result is 404.

Separated:
- **Model binding** — obtain/convert request values into action arguments/models.
- **Model validation** — determine whether successfully bound values satisfy application validation rules.
- Malformed JSON is encountered by the JSON input formatter/deserializer during body binding.

Learned the main `[ApiController]` conveniences:
- automatic 400 responses for invalid model state;
- binding-source inference;
- API-oriented error responses / Problem Details.

## Action results and HTTP semantics

Clarified:
- `Task<T>` — typed success data.
- `Task<IActionResult>` — flexible HTTP action result.
- `Task<ActionResult<T>>` — typed success payload plus ability to return results such as `NotFound()`.

Existing habit of `Ok(value)` is valid and explicit; returning `T` directly is also supported by `ActionResult<T>`.

Reviewed:
- GET success → 200
- POST resource creation → 201, often `CreatedAtAction` with Location
- DELETE success with no body → 204
- missing resource → commonly 404
- PUT conventionally represents full replacement/update; PATCH represents partial modification.

Important correction:
**Idempotent does not mean identical responses. It means repeating the operation has the same intended effect on server state.**

## Middleware vs MVC filters

Derived the boundary:
- **Middleware** is oriented around the HTTP request pipeline.
- **Filters** are oriented around MVC/controller/action execution.

Examples:
- whole-request timing and global exception handling → middleware;
- controller/action name, action arguments, and action-specific timing → action filter.

## Configuration and Options pattern

Moved from direct `IConfiguration` lookup to the typed Options mental model.

- `IOptions<T>` → stable options value.
- `IOptionsSnapshot<T>` → scoped/per-request snapshot.
- `IOptionsMonitor<T>` → singleton-friendly access to current/reloaded options.

Connected this back to DI:
A singleton consuming `IOptionsSnapshot<T>` creates the same lifetime mismatch/captive-dependency problem as a singleton capturing another scoped service.

Configuration can be type-correct but semantically invalid. Learned `ValidateOnStart()` as a fail-fast mechanism for required configuration.
