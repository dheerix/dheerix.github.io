## DSA — Sliding Window

### Longest Substring Without Repeating Characters

Started from the natural idea of maintaining a set of characters and removing earlier entries when a duplicate appears.

The key correction was that removing one character is not always enough. The left side must keep shrinking **while** the incoming character is still duplicated.

### Cold implementation

```csharp
public class Solution {
    public int LengthOfLongestSubstring(string s) {
        HashSet<char> seen = new HashSet<char>();
        int maxLength = 0;
        int right = 0;
        int left = 0;
        for(right = 0; right< s.Length; right++) {
            
            while(seen.Contains(s[right])) {
                seen.Remove(s[left]);
                left ++;
            }
            seen.Add(s[right]);
            maxLength = Math.Max(maxLength, right - left +1);
        }
        return maxLength;
    }
}
```

### Mental model

**Variable-size sliding window:** expand `right`; shrink `left` until the window becomes valid again.

Invariant: before measuring the window, `[left..right]` contains no duplicate characters.

Although the implementation contains a `for` and a `while`, it is O(n) average rather than O(n²): each character is added at most once and removed at most once. This is an example of amortized analysis.

### Last-seen optimization

Derived the dictionary variant without prompting:

- Store `character → last seen index`.
- On a repeat, jump `left` directly to `previousIndex + 1`.
- Use `Math.Max(left, previousIndex + 1)` so the left boundary never moves backward.

### Fixed-size sliding window

For maximum sum of a subarray of size `k`:

**add incoming, subtract outgoing.**

```csharp
public int MaxSum(int[] nums, int k)
{
    int windowSum = 0;

    for (int i = 0; i < k; i++)
        windowSum += nums[i];

    int maxSum = windowSum;

    for (int right = k; right < nums.Length; right++)
    {
        windowSum += nums[right];
        windowSum -= nums[right - k];

        maxSum = Math.Max(maxSum, windowSum);
    }

    return maxSum;
}
```

Distinction:
- Fixed window → size remains `k`.
- Variable window → expand and shrink according to a validity condition.

## .NET — CancellationToken

### Request cancellation

ASP.NET Core/Kestrel can detect an aborted/disconnected HTTP request and signal cancellation through:

```csharp
HttpContext.RequestAborted
```

The application must still propagate and observe cancellation for cancellable work to stop.

### Cooperative cancellation

Passing a `CancellationToken` does not forcibly interrupt CPU code.

```csharp
for (int i = 0; i < 10_000_000; i++)
{
    token.ThrowIfCancellationRequested();
    DoCpuWork(i);
}
```

Key idea:

**Cancellation requested ≠ operation forcibly terminated.**

.NET uses cooperative cancellation so operations can stop at safe boundaries and avoid leaving shared state/resources inconsistent.

### CancellationToken vs CancellationTokenSource

- `CancellationToken` observes a cancellation signal.
- `CancellationTokenSource` produces/signals cancellation.
- `RequestAborted` represents the HTTP request/client lifetime.
- A timeout CTS can represent an application-defined operation deadline.
- `CreateLinkedTokenSource` can combine multiple cancellation reasons.

### Business-operation boundary

The lifetime of an HTTP request is not necessarily the lifetime of a business operation.

After a durable business commit, required downstream work should not blindly depend on whether the browser remains connected. Durable handoff patterns such as the **Outbox Pattern** can separate business completion from request lifetime.

## .NET — Dependency Injection Lifetimes

### Lifetimes

- **Singleton** → one instance for the application's DI-container lifetime.
- **Scoped** → one instance per scope; normally one HTTP request in ASP.NET Core.
- **Transient** → a new instance each time the DI container resolves the service.

Important correction: transient is tied to **resolution**, not request completion or method-call count.

### Captive dependency

A singleton directly capturing a scoped dependency is a lifetime mismatch:

```text
Singleton
   ↓
Scoped
```

A longer-lived service can accidentally retain a dependency designed for a shorter scope.

When a singleton genuinely needs scoped work, create a temporary DI scope via `IServiceScopeFactory` and resolve the scoped service inside it. For EF Core scenarios, `IDbContextFactory<TContext>` can also be appropriate.

### Singleton concurrency

Singleton instances are shared across concurrent requests. Mutable state inside them must therefore be designed for concurrent access.

A plain mutable `Dictionary<TKey,TValue>` is not safe for concurrent writes.

### IMemoryCache

`IMemoryCache` provides process-local in-memory caching with concurrency support, expiration/eviction behavior, and cache-entry configuration.

Important architectural distinction:

- `IMemoryCache` → local to one application process/pod.
- Distributed cache → shared across application instances.

Thread safety inside one process and distributed cache consistency are different problems.

## ASP.NET Core — Middleware / Request Pipeline

### Core mental model

Middleware forms an async chain. A component can perform work before and after:

```csharp
await next(context);
```

Conceptually:

```text
REQUEST
   ↓
middleware A — before
   ↓
middleware B — before
   ↓
controller / terminal endpoint
   ↑
middleware B — after
   ↑
middleware A — after
   ↓
RESPONSE
```

This explains how logging can measure the entire downstream request and how exception middleware placed early in the pipeline can catch exceptions thrown later by a controller: exceptions propagate back through the awaited async call chain.

### Short-circuiting

Middleware can return without calling `next`, preventing downstream middleware/endpoints from executing.

### Authentication vs Authorization

- Authentication → **Who are you?** Validate credentials/token and establish `HttpContext.User`.
- Authorization → **Are you allowed to do this?** Evaluate claims/roles/policies against endpoint requirements.

Authentication should precede authorization because authorization relies on the established principal.

Status distinction:
- **401** → authentication is required or was not successfully established.
- **403** → identity is known, but access is not permitted.

### Use / Run / Map

- `Use` → participate in/wrap the pipeline and optionally continue.
- `Run` → terminal middleware; no downstream `next`.
- `Map` → branch the pipeline based on a path.
- Endpoint mapping such as `MapControllers` / `MapGet` registers routed endpoints.

Even when `Run` terminates downstream execution, upstream middleware still resumes after its awaited `next` completes.
